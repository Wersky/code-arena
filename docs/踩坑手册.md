## 42. 把 bug 钉成「现状断言」之后，修好它测试反而会红

**现象**：上一轮发现「`10-J-Q-K-A` 顺子认不出来」，为了防"以为它已经支持"，
我在 `tests/verify_hands.gd` 里写了一条**现状断言**：`evaluate_type(...) != STRAIGHT`。
这一轮按主人要求支持 A 高位，代码改对了，**测试立刻红**——红的是那条"防御性断言"。

**根因**：现状断言的语义是「当前这样」，期望断言的语义是「应该这样」，两者在同一行代码里长得一样。
规则一改，现状断言就从"护栏"变成"反向断言"。本轮还有同类三处：
`smoke_test` 里「起始牌库 9 张」「起始牌库有点数重复」——换 52 张牌池后必红。

**修法**：
① 改规则/改数据形状时，**先把"钉现状"的断言翻正**（本轮：改成 `== STRAIGHT`，另加皇家同花顺一条）；
② 断言文案里写清是现状还是期望（"已知缺口：…" / "应该…"）；
③ 换牌池这类改动，测试数字跟着变是正常的，**不要为了让它绿而把断言删掉或放宽**。

**防复发**：看到断言里出现 `!=`、`<`、"目前不"这类字眼，先问一句
「这是期望，还是我在给 bug 立碑？」——立碑可以，但要在交接文档里登记，改的时候一起拆。

**本轮连带作废的刻度**：牌池从 9 张换 52 张后，旧目标分（2050~5220）有 6 关被判「保过」、
整局通关率虚高到 59%。按坑 33 / 36 重校：480 局定分位数 → 目标分取 q10 附近 →
再用两批独立种子复核，最终 87%~93% / 37%。

## 41. 抠白底时「白色角色」会被一起挖穿 —— 颜色分不开，必须走形状

**现象**：把 52 张样张（白纸卡面）拆成「角色层 + 角标层」交给引擎重绘。
spades/hearts/diamonds 都没事，**clubs（白发龙娘）整片身体被挖空**——
白裙、白脸、白发全变成透明，只剩轮廓线和几处阴影碎片。
而逐像素 diff **只报 8 个不一致**，看起来"几乎完美"，肉眼却是残的。

**根因**（三层，逐层踩）：
1. **白身体与纸面是同一个色值**：实测 clubs/5 纸面 = `(255,255,255)`，
   身体也是 `(255,255,255)`，柔光才到 `(249,246,250)/(253,253,253)`。
   所以"近白 → 透明"的洪泛**必然**顺着柔光的开口漏进身体。
   更坑的是 diff 脚本把纯白当纸面跳过，**指标全绿**（自欺的验收标准比没有更危险）。
2. **卡边是一圈闭合墨线**：从卡外洪泛时纸面进不去（被墨边挡住），
   整张卡会被判成"角色"，变成一个巨型连通块，角标再也识别不出来。
3. **角标不是固定矩形**：`clubs/J` 的字母 J 会伸进右下角标区，
   按矩形清角标会把角色切掉一块。

**修法**（`tools/make_card_assets.py`）：
1. 先把 mask 的外圈 6px 清掉（拆掉闭合墨边），再谈洪泛；
2. 非纸像素（任何通道 <254）当墨迹，**闭运算**（`MaxFilter(5)` → `MinFilter(5)`）
   把柔光轮廓上 1~2px 的缺口接起来；
3. **从卡外洪泛，进不去的区域就是角色**（含被包住的白身体），
   alpha 按轮廓给、颜色取原值 → 白身体恢复成纯白，叠在白纸上无缝；
4. 角标用**连通块 + 窗口**判定：只有整个落在左上/右下角标窗口内的连通块才算角标，
   角色碎片（翼/尾巴/字母）自然被排除；
5. 验收不看"看起来对"，看**合成回去和样张的逐像素差异**（现在是 8px/张，就是重画的卡边）。

**防复发**：
- **白色主体做抠图，先量色值再定策略**。"近白洪泛"只对"主体与背景不同色"成立。
- **闭合边框会挡住背景洪泛**——先拆边框再洪泛，别指望它自己让路。
- **像素级 diff 的跳过条件要写对**：把主体颜色当"背景"跳过，等于把 bug 筛掉。
  这次是先把角色层单独铺到深色底上看，才一眼看出来的。

## 40. 换玩法时，旧玩法的"目检钩子"会变成哑炮

**现象**：把代码卡换成扑克牌之后，`--shot=syntax` / `--shot=memeverify` 还在，
但里面写死了 `["while_kw", "if_kw"]` 这种旧卡 id。运行不报错，
截图出来是一张**空手牌**——因为新卡 id 是 "H3"/"S3"，解析不出来，返回 null 后被静默跳过。

**根因**：调试/目检代码里的**数据是硬编码的**，它们不参与类型检查（都是 String），
换玩法时编译器不会提醒，运行时也不抛错。

**修法**：
① 换玩法的同一轮里，把 `main.gd` 的截图分支逐个过一遍——**每个 screen 名字都跑一次**；
② 目检钩子里的牌 id 一律走新的解析函数（`_card_from_id`），失败时 `push_error` 而不是静默返回；
③ `docs/04-基础玩法.md` 的"目检"一节列出全部可用 screen，改玩法时按清单核对。

**防复发**：**目检钩子 = 测试代码**，换数据结构时它和测试要一起改。
编译通过不等于跑得对——硬编码字符串是类型系统的盲区。

## 39. 功能一层层加上去，第一眼就没人看得懂了

**现象**：梗卡版本叠了四层——AI 娘主题倍率、Token 预算与惩罚、23 张混杂梗卡（饭/玄学/杂项/专属）、
关卡特殊规则。主人原话：「卡牌太乱了」「要简洁」。

**根因**：每一层单独看都是合理的，但它们是**并列叠在同一个结算公式里**的：
玩家想知道"我下一步该干什么"，得同时懂主题、懂 Token、懂卡类型、懂关卡规则。
**每加一层，新玩家的理解成本是加法，但读懂一手的成本是乘法。**

**修法**：**砍到只剩一条主线**——代码顺序对不对 → 给分 / 不给分。

- 卡：23 张 → **8 张，只有代码卡**
- 规则：7 条语法 + 7 个结构 → **3 条语法 + 3 个结构**
- 计分：`(base+flat)×mult−Token罚` → **`Σ卡面分 + Σ结构加成`**
- 关卡：目标分 + 回合 + Token + 特殊规则 → **目标分 + 回合**
- 流程：菜单 → 选 AI 娘 → 战斗 → 奖励 → 商店 → 关卡 → **菜单 → 战斗 → 奖励 → 关卡**

砍下来的东西**代码全留着**（`meme_cards.gd` / `meme_combo.gd` / `ai_select.gd` / `shop.gd`），
只是不进主流程。存档不删，随时能当"可选构筑层"加回来。

**防复发**：判断"该不该加这一层"只问一句——
**能不能用一句话说清玩家下一步该做什么？** 说不清就不加。
要说清两条规则，就让它们**语义相关**（while→if 和 try→catch 都是"配对"），
不要拿"主题加成"和"Token 预算"这种正交维度去稀释注意力。

## 38. 终端「输出即回显」把玩家正在拼的程序卷走了

**现象**：玩家点第二张卡凑出结构加成（比如 `while` + `if` → 护栏），
控制台一播报 `→ 代码结构【护栏】…`，**命令行里刚拼好的 `while if` 就消失了**，
只剩一个空提示符。玩家看不到自己写到哪儿，接着点下一张时完全靠记忆。

**根因**：`PromptConsole.append_line()` 照抄了终端语义——
"有输出 → 先把当前命令行回显进历史区，再清空实时命令行"。
这语义对「运行之后打结算明细」是对的（那条命令确实交付了），
但**拼装过程中**的即时播报（结构加成 / AI 娘吐槽）也走了同一条路，
于是把还没提交的半成品程序一起冲走了。

**修法**：`append_line(text, color, echo := true)` 加 `echo` 参数。
拼装期间的即时播报一律 `echo=false`：只往历史区加一行，**不动命令行**。

**防复发**：把「终端样子」和「终端语义」分开看。
凡是**玩家还在编辑**的输入区，任何后台播报都不许碰它；
只有"提交"这个动作才允许让输入区被 consume 掉。

## 37. q05 判定用的样本量不够 → 同一批关卡换批种子就翻面

**现象**：L9 目标分 376，在校准批（seed=424242）q05=366 判定 OK；
换 held-out 种子（seed=777333）q05 变成 **389**，判定翻成「保过」。
把 L9 抬到 400 后，校准批的整局通关率又从 37% 掉到 28%（掉出 35%~55% 验收带）。

**根因**：模拟器 `DEFAULT_SIMS := 60`——**每关只跑 60 局**。
q05（5% 分位数）在 60 个样本上就是**第 3 低的值**，标准误差能到 ±20 分。
文档里写的校准口径是「480 局」，但实际跑的一直是默认的 60 局。
于是「目标分 > q05」这条判定建在一条**抖动的曲线**上：换个种子就穿帮。
（顺带：L9 的 q10−q05 间距只有 10 分，60 样本下几乎必然被噪声吃掉。）

**修法**：
① 校准/验收**一律 `--sims=480`**，别用默认值；
② 模拟器在 `_sims < 240` 时**明确警告**"q05 判定不可信"；
③ 文档与交接里的「480 局」是**硬要求**，不是建议。

**防复发**：任何**分位数判定**（q05 / q10 / 保底分）都要先问
**「这个分位数在当前样本量下，标准误差是多少」**。
n=60 时 5% 分位 = 第 3 低值，噪声与效应同量级，判定等于掷硬币。
分位数判定要 **n ≥ 20/分位比例**（5% → n ≥ 400）才谈得稳。

## 36. 目标分要**跨种子批次**都高于 q05 —— 单批校准会把「保过关」漏进下一批

**现象**：L9 目标分 376，在校准批（seed=424242）里 q05=366，判定 OK；
换一批 held-out 种子（seed=777333）再跑，q05 变成 **389** —— 目标分反而**低于** q05，
判定翻成「保过」。

**根因**：q05 是**估计量**，240~480 局的经验 5% 分位数本身带方差。
目标分只按**校准批**的 q05 定，就等于把目标分钉在了一条抖动的曲线上，换批就穿帮。
关卡越靠后、分布越窄，抖动的绝对值越大（L9 的 q05 两批差了 23 分）。

**修法**：目标分按**多批种子的 q05 最大值**定，留出余量；
L9 从 376 抬到 **400**、L10 从 380 抬到 **420** 后，三批种子全部 OK。

**防复发**：重校目标分的验收动作是**至少三批互不相关的种子各跑一遍**，
要求每批都是 OK——单批 OK 不算数。种子基准用大质数步长（7919）保证洗牌序列不相关。

## 35. 顺序决定合法性之后，「2 种固定排列」的贪心就找不到合法程序了

**现象**：换成代码语法机制后，平衡模拟的贪心均分只有 309~592（连携机制时代是 558~1067），
而且**整局通关率掉到 0%** —— 看着像难度炸了，其实是**搜索器不会玩新游戏**。

**根因**：连携机制下顺序无意义，"分数降序 + 饭类垫底"两种排列就够了。
语法机制下**顺序就是合法性**：`while` 必须紧跟 `if`、`try` 必须配 `catch`。
把牌按分数降序排，得到的排列几乎必然语法非法 → 引擎只给"每张卡 1 分" →
贪心均分被自己拖垮 → 校出来的目标分全线偏低。

**修法**：贪心换成**束搜索**（`BEAM_WIDTH := 12`）：
逐位往下拼，每一步保留 score + 语法前缀健康度最好的 12 条前缀，
`CodeProgram.prefix_issues()` 给出「还能不能救活」的信号（hard = 后面补牌也救不回来，
soft = 补牌能修）。束搜索跑完的平均分才代表「会玩的人」的水平。

**防复发**：**机制的胜负维度一变，搜索器就得跟着换**。
从"凑组合"换成"排顺序"时，枚举排列的思路直接作废；
新机制的搜索空间要用能表达新约束的启发式（这里是"前缀合法度"）去剪枝。

## 34. while 的护栏 if 被当成嵌套层 → 套娃判定恒错一层

**现象**：`CodeProgram.depth()` 算出来是 3，预期 2；套娃（嵌套深度 ≥ 2）的
触发条件因此被错误地提前/推迟命中。

**根因**：`while` 后面紧跟的那个 `if` 是**循环护栏**（限制循环次数），
不是"又开了一层嵌套"。但代码里 `if_kw` 一律 `d += 1`，护栏也被算成一层。

**修法**：`if_kw` 分支里先判 `is_guard := i > 0 and ids[i-1] == "while_kw"`，
护栏不计入深度。

**防复发**：写深度/嵌套类判定前，先把**每种语句的语义角色写下来**
（护栏 / 块头 / 块尾），再逐个归类；"同一种关键字在不同位置的语义不同"
是这类 bug 的通用来源。

## 33. 换机制后目标分刻度**整体**作废 —— 旧刻度会让游戏根本不可能通关

**现象**：梗卡机制上线后，右上角一直显示「本关 0 / 1250」，
但实测单回合只能拿 **58 分**、整关 3 回合顶多 ~180 分。
1250 分在新机制下是**数学上不可能达到**的目标 —— 每一关都必死，整局通关率 0%。

**根因**：`scripts/data/level_pool.gd` 的目标分是**旧命令行机制**用
`balance_sim.gd`（几千级刻度）反推出来的。机制一换，**分数的量纲跟着换了**
（几千 → 几百），但目标分没跟着换。
两套机制的分数根本不是同一个东西：旧机制 6 段命令行的顺序层能到 1228 分，
梗卡机制 5 张卡一个回合才 60~140 分。

**修法**：**换机制 = 重校刻度**，不是改改数字。
① 新写模拟器 `tools/balance_sim2.gd`（**旧脚本保留为存档，不要覆盖** —— 它是旧机制的证据）；
② 跑出每关的分数分布与 q05；
③ 目标分落在新刻度区间（本轮实测 **246~633**）；
④ 回归里加一条**刻度断言**：所有 `target_score` 必须落在 100~900，
防止下次又把手写的一堆大数字塞回去。

**防复发**：任何"换计分机制"的改动，第一件事是问
**「分数的量纲变了吗」**。变了就得连同目标分、平衡模拟器、回归刻度断言一起重做。
目标分的数字**永远来自实测分位数**，不来自上一代机制，也不来自手写。

## 32. 平衡模拟别贪多排列组合 —— 上一轮 agent 为此耗掉 1 小时 46 分

**现象**：上一轮做平衡模拟时，为了"更接近最优解"，把贪心搜索从
"2^8 子集 × 2 种排列"扩到了"再加上 N 种排列 / 全排列"，结果模拟脚本跑了
**1 小时 46 分钟**还没完，任务卡因长时间无笔记被插件回收，成果差点记不上账。

**根因**：贪心搜索量是**指数级**的。手牌 8 张 → 256 个子集；
每个子集再乘 K 种排列 → 256×K 次 `evaluate()`。
K 从 2 涨到 8，评估量就是 4 倍。每回合 4 倍 × 10 关 × N 局，
再叠加 GDScript 的解释执行开销，直接从天级掉到小时级。
而且**边际收益极低**：排列只影响"下一张 X 翻倍"这类连携的落点，
2 种排列已经覆盖了绝大多数收益，再加排列只是把分数抬高几个点。

**修法**：① **贪心只做 2 种排列**（本轮：分数降序 + 饭类垫底）；
② **同一个多重集只算一次**（同 id 的不同副本视为同一张，用排序后的 id 串做 key 去重）；
③ **先拿趋势再精调**：`--sims=40` 先跑（40 秒），确认曲线形状对了再上 `--sims=120`；
④ 把得分矩阵 `--dump` 落盘，**离线**搜阈值，不要为了试不同目标分反复重跑模拟。

### 32·补 · 相邻局的种子步长太小 → 校准出的目标分会过拟合

**现象**：第一版目标分是在 `run_seed = 424242 + s*17`（s=0..119）这 120 局上校出来的，
120 局复跑看着全对（每关 87%~95%、整局 42%）。
换一批种子重跑 —— `run_seed = 90210 + s*17` —— 结果变成
L7 通过率 94%→81%、L10 87%→83%、**整局 42%→29%**，直接掉出验收线。
再换 `--seedstep=7919` 又变成另一组数（L10 77%、整局 32%）。

**根因**：`run_seed` 相邻只差 **17**，而每关的洗牌种子是
`run_seed + 关卡 id 哈希 + 7717` —— **相邻局的洗牌序列是相关的**，不是独立采样。
所以"120 局"的有效样本量远小于 120，分位数（尤其 q05 / q10）估得很虚，
在它上面搜出来的阈值自然只对那一批种子成立。

**修法**：① **相邻局种子用大质数步长**（本轮默认 `--seedstep=7919`），保证各局洗牌互不相关；
② **校准样本要够大**（本轮 480 局），分位数的标准误才压得住；
③ **必须留 held-out 种子做复核**：校准用 base=424242（480 局），
复核用 base=777333（240 局，step 7919）与 base=31337（240 局，step 104729）
—— **三批都在验收线里才算过**：
通过率分别 95/94/91/93/91/90/89/92/90/88 %、96/92/94/94/93/88/91/93/90/92 %、
94/93/92/92/94/90/93/93/94/89 %，整局通关率分别 **41.9% / 46% / 44%**。

## 31. 侧栏数值列对不齐 —— 根因是「数值被塞进了铭牌控件里」

**现象**：左侧竖栏 4 行 HUD（关卡 / Token / 算力 / AI娘）看着"差不多齐"，
但数值长短不一时整列就散了 —— `L1` 和 `0 / 9` 的右边缘差了十几像素，
`DeepDeek` 和 `2 / 9` 又是另一条线。肉眼几乎看不出，**用像素坐标一量就露馅**。

**根因**：早期实现把**数值直接拼进铭牌（Label）控件的文本里**，
比如一个 Label 写 `"L1"`、另一个写 `"0 / 9"`。
控件的**右边缘由文本长度决定**，文本一变，右边缘就变 → 整列不可能对齐。
控件本身的 `size` 还会因为文字变宽而重排，抖动会往下传。

**修法**：**数值必须独立成列，右对齐**。
① 铭牌控件（图标 + 标签）固定宽度，**只放图标和标签文字**；
② 数值单独一个 Label，挂在同一行的 HBox 末尾，
`horizontal_alignment = RIGHT` + `size_flags_horizontal = SIZE_EXPAND_FILL`；
③ 所有行**走同一个行工厂**（本轮是 `UiKit.icon_row()`），不许散着写字号覆盖；
④ 改完**用像素坐标验**，别用眼睛看 —— 量 `global_position.x + size.x`，
确认所有行的数值右边缘落在**同一条竖线上**（本轮实测 220.0，标签列左边缘统一 56.0）。

**防复发**：任何"一列要对齐"的 UI，数值/文本**一律独立成控件 + 右对齐**，
不要用空格/固定宽度凑。验收用**像素坐标**，不用肉眼。

## 30. 插件心跳只认 `task_update` —— 长任务不写笔记会被超时回收

**现象**：agent 明明一直在跑（文件时间戳一路在动），任务卡却自己从 `in_progress`
被插件改回 `pending`，owner 也被清掉，最后一次 `task_update(done)` 直接被拒：
`当前 owner 是 xxx，你以 (未提供 owner) 身份无权改状态`。

**根因**：taskswarm 插件的"心跳"就是**任务笔记**。它按 `task_update` 写入的时间戳判断
agent 是否还活着 —— **只写文件、不写笔记 = 心跳断掉**。
默认阈值是 `TASKSWARM_STALE_MINUTES=30`（`in_progress` 超过 30 分钟没有任何笔记 → 自动回收）。

**修法**：① 长任务里**每 ~10 分钟就补一条 `task_update` 笔记**，内容可以是"进度 N%｜已完成 X｜下一步 Y"；
② 被回收后由主代理 `force:true` 恢复 owner 并重新 claim；
③ 补记笔记时**显式传 `owner`**（否则自己的身份对不上，会被拒）；
④ 每次 MCP 调用都**显式传 workspace**（`D:/zcode-work/godot`），别靠默认值。

> **本轮实例**：上一轮的 `ui-meme` 任务从 09:41 起就没再写过笔记，
> 任务卡 10:53 被插件超时回收，但那个 agent **代码一直改到 17:56** —— 活儿是真做完了，
> 只是没人记得，最后靠主代理代写笔记补账。同一轮里另一个 agent
> 在平衡模拟那一步跑了 1 小时 46 分没写笔记，任务被回收，成果差点记不上账。

**防复发**：把"写笔记"当成心跳而不是当成汇报。干活干得再漂亮，
30 分钟不写笔记就等于失联。写笔记顺手把"已完成/下一步"也带上了，本来就不亏。

## 29. 契约的算例和自己的规则表打架时，以规则表为准

**现象**：设计契约 `docs/01-新机制设计.md` 的 C.4 章给了 4 个可复现算例，
但按算例反推出来的分数，**跟契约自己 C.2/C.3 的规则表算出来的不一样**——
差 5 处：例1 通用 flat 少算 8、例2 漏乘 `str_no_role_head` 的 ×0.93、
例3 漏判 `str_task_misplaced` 与 `str_format_before_example`、例3 的 `str_gap` 用了下限值、
例4 漏判 `str_compact`。两边差得不多，但**哪边是对的**必须定死。

**根因**：算例是**手算**的，规则表是**规则**。手算必然漏项，
而且漏项的方向不固定（有的多算、有的少算），没法靠"两个数取平均"糊过去。

**修法**：**规则表是唯一真值**（它是可执行的、能被代码逐条判定的）；
算例是**推导结果**，错了就改算例。
具体做法：让 data-layer 先按规则表实现，再用脚本把 C.4 四例实算出来，
把结果回写契约文档；mech-design 复核后确认「规则表不动、算例改成实现实测值」。
最终基准值 = **1228 / 1045 / 799 / 113**，无顺序层基线 = **929**，
并落成 `tests/verify_c4.gd` 作为**契约铁律 2** 的执行体。

**防复发**：**任何"文档里的数字"都必须有对应的可执行断言**。
文档和实现对不上时，先问"哪边是可执行的" —— 那边才是真的。
`verify_c4.gd` 因此成为改计分规则后的必跑项（对不上就是回归，先查实现再改文档）。

## 28. 改过 `class_name` 不跑 `--import`，headless 测试会**假绿**

**现象**：改完代码跑无头测试，输出是 **「38 项检查，0 项失败」** —— 看着全绿，
但用例数只有 38（当时应该是 98）。更坑的是**退出码是 0**，
脚本里如果只判断"有没有失败"就会一路绿灯放过去。

**根因**：Godot 只在 `--import` 时把 `class_name` 写进 `.godot/global_script_class_cache.cfg`。
本轮新增了 `AiData` / `AiTaste` / `AiPool` 等全局类，

**修法**：① 改过 `class_name`（新增 / 删除 / 改名 / 改 `extends`）后**必须先跑**
`godot --headless --path . --import` 再跑测试；
② 判据不能只看"失败数"，要**看用例总数**：
smoke_test 必须是 **204**、verify_c4 必须是 **4**、meme_selftest 必须是 **219**，
少于总数一律按失败处理；
③ 出现 `Failed to load script` / `Parse Error` / `Could not resolve class` 一律按失败处理，**哪怕退出码是 0**。

> ⚠️ **用例总数会变**：往 smoke_test 里加断言时，**总数要同步更新**（98 → 204）。
> 判据"用例数 == 总数"里的"总数"是活的，每次加断言都要重新数一遍再改文档，
> 否则这条判据自己就过期了。

**防复发**：把这写进铁律并贴进 `docs/进度交接.md` 第二节。
CI 里校验"用例数 == 总数"，而不是校验退出码。

## 27. 关卡目标分低于该关得分的 5% 分位数 = 这一关是"保过关"

**现象**：新机制上线后重校目标分，10 关里有 2 关（L2、L9）的**贪心通过率是 96% / 97%**，
比其它关高出 6 个点，怎么看都像"这两关白送"。

**根因**：目标分是**上一代机制**估出来的（乘系数 ×1.27），
新机制让分数整体上浮之后，两关的目标分**落在了实测得分分布的 5% 分位数（q05）以下** ——
也就是说，**就算打出最差的一局也能过**。这关根本没有失败风险，
"评测未通过"的分支在这两关上永远不会触发。

**修法**：给 `balance_sim.gd` 加一列 **q05 保底判定**：
`目标分 ≤ q05` → 标记「保过」，说明这关必须重校。
然后把 10 关目标分**全部抬到各自 q05 之上**（最紧的 L2 只留 67 分裕度，是刻意留的最小失败窗口），
同时把偏松的 L1 / L6 / L7 回调，避免整体难度被抬高过头。

**防复发**：**目标分不能靠系数估算，只能靠实测分位数反推**；
而且判定标准要不止"通过率落在某个区间"，还要有一条**结构性**的检查
（目标分 > q05），否则会出现"通过率数字好看但实际是白送"的关卡。

> 这条对**两套机制都成立**：旧命令行机制用 `balance_sim.gd`（几千级刻度）校，
> 梗卡机制用 `balance_sim2.gd`（几百级刻度）校 —— 但"目标分 > q05"这条结构判据一模一样。
> 另外换机制时别忘了**刻度整体作废**（见坑 33）。

## 22. 像素风不是"把图缩小"——必须三步后处理

**现象**：直接让模型出像素风提示，出来的图**看着是像素画，放进游戏却不对**——
缩放后边缘是软的、调色板有几百种颜色、插画是"插画风格"而不是"游戏素材"。

**根因**：模型输出的是 1024/1536 的大图。所谓"像素风"只是**画风描述**，
真正的像素画需要**低分辨率网格 + 有限调色板 + 硬边放大**三件事，模型不会替你做。

**修法**（`pixelize_arena_art.py`）：
1. 面积平均缩到低分辨率网格（卡面 64×64 / 立绘 96×96 / 背景 384×256）；
2. 量化到有限调色板（图标 16 色 / 立绘 32 色 / 背景 48 色，背景加抖动避免渐变断层）；
3. **最近邻**放大回目标尺寸 —— 硬边像素块，不糊。

**顺序有讲究**：边缘融合 → 像素化 → 半身像裁切。
半身像**必须在像素化之后裁**，且裁切坐标要对齐到整数像素块，
否则切出来的边不是像素对齐的，再放大就花了。

**防复发**：像素风项目的贴图必须在 Godot 里用最近邻采样
（`rendering/textures/canvas_textures/default_texture_filter=0`），
否则引擎默认线性过滤会把像素块糊掉。

## 20. 贴图自带背景，贴到场景上露出一圈生硬矩形边

**现象**：主菜单把主角立绘贴到场景背景上，四边出现明显的矩形接缝——
因为这张图自带另一套深蓝科技室背景，和场景不是同一张。

**根因**：不透明矩形 PNG 直接贴，必然有边。

**修法**（`blend_arena_hero.py`，三步）：
1. 整体 RGB 往场景基色混 30%（色调先靠近）；
2. 以人物为中心做**径向 alpha 渐隐**（`R_INNER` 内实心、`R_OUTER` 外全透）；
3. 渐隐带内同时把 RGB 压向场景色（避免出现"半透明矩形"）。

**防复发**：合成主体的贴图要么预裁成天然不规则的形状（羽化、遮罩），
要么给它加一个明确的"画框"当设计元素；硬边矩形 + 无边框 = 露馅。

## 19. 第二次缩进错位：`_current = screen` 缩进进了 if 块，界面永远不销毁

**现象**：
1. 端到端流程截图停在战斗界面，明明已经点过「继续」却没到奖励界面；
2. 调试时发现 `_current` 永远是 `null`；
3. 每次切换界面，旧界面都没有被 `queue_free()` 销毁，**新界面叠在旧界面上面**——
   肉眼看不见（新的全屏盖住了旧的），但旧界面还活着、还在收输入事件，内存也在涨。

**根因**：

```gdscript
func _swap(screen: Control) -> void:
	if _current != null:
		_current.queue_free()
		_current = screen      # ← 缩进在 if 块内
```

`_current` 初值就是 `null`，所以 `if` 永远不进，`_current = screen` **一次都没执行过**。
所有界面都能显示（`add_child` 在 if 外面），所以表面上完全正常——只是路由状态全丢。

**修法**：把赋值挪出 if 块。

**防复发**：
- 加 `debug_screen_count()` 测试接口，断言**任何时刻挂载的界面数恒为 1**，
  连续快速切换 10 次后仍为 1；
- 写了 lint 扫全项目：找"同一个变量在 if 块内被赋值、紧接着在块外又被赋值"的疑似缩进错位，
  本次扫描结果为 0（除本条外）。

**这条坑的教训**：Python 出身写 GDScript，缩进语义是**块级**而不是 Python 的"同一行 = 同一个块"，
一个 Tab 的差异就能让一行代码彻底不执行，而且**不报错**。
本项目因此栽了两次同款（另一条见第 4 条 `end_turn()` 的 `hand.clear()`）。
**凡是"看起来像该在外面执行"的关键语句（赋值、清理、状态推进），写完都要单独看一眼缩进。**

## 18. 地图解锁判定写成 `<`，结果第一关也进不去

**现象**：玩家进游戏点「开始新的一局」，地图上 10 关全部显示「🔒 未解锁」，包括 L1。

**根因**：`run.level_index` 的语义是**已通关关数**（开局为 0），但解锁判定写成了

```gdscript
var unlocked := _level_index(l) < run.level_index   # 0 < 0 → false
```

正确语义是 `序号 <= 已通关数`（已通关的关 + 当前该打的那关）。

**修法**：

```gdscript
var idx := _level_index(l)
var done := idx < run.level_index
var unlocked := idx <= run.level_index
```

**防复发**：原来的 81 项冒烟只检查界面"能不能构建"，不检查"状态对不对"，
所以这个 bug 一路放行到真人试玩才暴露。现在补了 `debug_level_states()` 测试接口，
断言"开局 L1 解锁、其余 9 关锁定"和"通关 3 关后 L1~L3 已通过、L4 可进、L5 仍锁"。

> **教训**：冒烟测试要同时覆盖**构建**和**状态**。只测"节点存在"的套件挡不住逻辑写反。

## 17. 结算结果弹窗被主控立刻切屏吃掉

**现象**：打完一关直接跳到奖励界面，玩家完全看不到"评测通过 / 未通过"的弹窗，
弹窗上的「继续」按钮是死代码。

**根因**：`_finish_level()` 里先 `_overlay.visible = true`，紧接着 **同步** `emit` 了 `level_cleared`；
主控收到信号立刻 `_swap(reward)`，把战斗界面连同弹窗一起 `queue_free()` 了。

**修法**：拆成两个信号——

- `level_cleared` / `level_failed`：**只记账**（`run.level_index += 1`、标记是否通过），不切屏；
- `advance_requested`：玩家点了弹窗上的「继续」才发，主控收到后才决定去奖励界面还是回地图。

**防复发**：任何"界面自己弹结果窗"的流程，**切屏必须由玩家操作触发**，
不能由状态信号同步触发。信号只传状态，不传"下一步去哪"。

## 16. 算力经济按"剩余回合"算，打完第一关连卡都买不起

**现象**：商店里刷新货架要 12 算力、卡牌要 40 算力，但过关只发 20 算力，
玩家进商店发现什么都买不起，刷新按钮点了也没反应，像坏了。

**根因**：算力公式是 `剩余回合 × 20 + 超出目标分 ÷ 10`，
可回合**总是会被用完的**（不过关就得重打），所以"剩余回合"几乎恒为 0，
实际只拿到溢出分那一丁点。

**修法**：改成 `关卡回合数 × 15 + 超出目标分 ÷ 10`——基础值跟关卡长度挂钩，
稳定在 45~90 算力/关，配合溢出分正好够每关买 1 张卡。

同时给商店加了**买不起时的明确反馈**：刷新按钮置灰 + tooltip 说明差多少 +
底部一行红字写"算力不足（0/12）——先通过评测赚算力：剩余回合 × 20 ＋ 超出目标分 ÷ 10"。

**防复发**：任何经济系统都要拿"玩家第一次进商店时买得起东西"当验收项。
「点了没反应」是最伤信任感的失败方式，宁可置灰也要给理由。

## 15. 新项目首次跑测试前必须先 `--import`

跑过。CI 脚本同理。

## 13. 卡名与牌库表对不上，起始牌组少一张

**现象**：`starting_deck()` 返回 24 张而不是预期的 20 张；
逐张统计发现「附上报错堆栈」这张卡**根本不在牌组里**。

**根因**：牌池里这张卡的标题写成了「给一段报错堆栈」，而 `starting_deck()` 的 picks 列表里写的是

**修法**：统一命名；`smoke_test.gd` 里加了「卡牌标题无重复」与「起始牌组 20 张」两项断言兜底。

**防复发**：任何"按名字取卡"的表（牌组 / 关卡 / 道具）都要配一条数量断言。
静默跳过是最难查的一类 bug。

## 12. 风险卡的幻觉惩罚被扣了两次

**现象**：一张风险卡打出后，扣分远超预期；单张风险卡直接算出负分被 clamp 成 0。

**根因**：`detect_combos()` 把幻觉的 −70 写进了牌型的 `flat`（UI 要显示这个数字），
`evaluate()` 又在结算末尾独立减了 70。同一笔惩罚算了两遍。

**修法**：`evaluate()` 累加牌型 flat 时**跳过 `hallucination` 这一项**（它的倍率照常乘），
惩罚统一在结算末尾扣一次。UI 仍显示 −70，玩家看到的和实际扣的一致。

**防复发**：牌型表里凡是"既进 flat 又在末尾单独扣"的项，都要在累加处显式排除。
`scoring.gd` 里已加注释标注。

## 11. 道具逐卡修正与关卡规则打架

**现象**：`HALF_RISKY` 关卡里风险卡基础分减半，但 `DeepDeek` 的"首张任务卡 ×2"仍按**原值**补了一份，
导致风险卡在这关反而比正常卡更值钱。

**根因**：基础分是"先按规则打折，再一次性加道具"的写法，工具函数拿不到打折后的实际值。

**修法**：改成 `per_card: Array[float]` 逐卡计算——先打折、再叠道具、最后求和。
所有道具效果改成对 `per_card[i]` 作用。

**防复发**：任何"逐卡"效果都要走同一张 per-card 数组，不要在总量上做加减。

## 10. `Array.filter()` 的返回值没有类型，`:=` 推断失败

**现象**：`var sft := pool.filter(func(i): return ...)[0]` → `Parse Error: Cannot infer the type of "sft"`。

**根因**：Godot 4 的 `Array.filter()` 返回无类型 `Array`，元素类型丢失。

**修法**：写一个显式返回类型的 helper：

```gdscript
func _item(effect_id: String) -> AiItemData:
	for it in AiItemPool.all_items():
		if it.effect_id == effect_id:
			return it
	return null
```

**防复发**：需要类型时用 `for` 循环或显式标注 `var x: AiItemData = ...`，不要依赖 `filter()` 的类型推断。

## 7. 关卡目标分手写 → 整局通关率 0%

**现象**：目标分按 400 / 700 / … / 9000 递增拍脑袋写完，
蒙特卡洛一跑，**贪心机器人都过不了 L7 之后的任何一关，整局通关率 0%**。

**根因**：贪心实测每回合得分上限只有约 500 分，10 关全裸装累计也就 5000 出头。
9000 的目标分在数学上不可达。而"裸装模拟"本身也不准——真实局内会不断拿到 AI 道具和卡牌。

**修法**：写 `tools/balance_sim.gd`，模拟**完整 Run**：逐关贪心打、过关发 1 件 AI 道具 + 买 1 张卡、
再打下一关。用它反推每关目标分，锚点规则是 **目标分 ≈ 该关贪心均分的 60%~70%**。

**防复发**：任何有数值曲线的系统都要配一个模拟器，改数值后跑一遍再定稿。
当前实测：贪心通过率 84%~97%，整局通关率 46%。

## 6. "禁打某类型"的关卡规则掐断能力上限，曲线出现回退

**现象**：为了让目标分逐关递增，把 L2 的目标抬到 L1 之上，结果 L2 通过率只有 77%、
L8 只有 71%；回头把目标压下去，曲线又出现 L8 目标 < L7 目标（玩家会当成 bug）。

**根因**：`NO_PERSONA` / `NO_EXAMPLE` 是从牌库里**移除**某类卡，等于直接砍掉约 20% 的得分天花板，
而目标分必须单调递增——两个约束互相打架。

**修法**：把规则从"禁打"改成"**该类型基础分减半**"。牌型结构完整（委托明确 / 范例驱动照样成立），
天花板不变，规则特色也保留，曲线恢复单调递增。同步把规则文案改成叙事化的说法
（"评审不认你的头衔" / "少样本不起作用了"）。

**防复发**：关卡规则只允许**压分数**，不允许**删牌**。需要限制牌型时用"必须包含 X 卡"这类
"不满足则减半"的软约束。

## 5. 地图 4 列排不下，第 4 章的按钮被裁掉

## 4. `end_turn()` 的 `hand.clear()` 缩进进了 for 循环体

**现象**：结算一回合后手牌不清空（8 张变 17 张），弃牌堆只有 1 张，牌库耗尽后手牌无限膨胀。

**根因**：

```gdscript
for c in played:
    discard_pile.append(c)
    hand.clear()      # ← 缩进在循环体内
```

`hand.clear()` 只在循环体里执行，空的 `played` 数组让它一次都不执行。

**修法**：提到循环外，并补上"整手牌作废"的小丑牌式规则：

```gdscript
for c in hand:
    discard_pile.append(c)
for c in played:
    if not discard_pile.has(c):
        discard_pile.append(c)
hand.clear()
```

**防复发**：Python 出身写 GDScript 要特别警惕缩进语义差异——同一个缩进在两种语言里含义完全不同。

## 2. 界面全部代码构建，零手写 .tscn

**决策**：除了 `scenes/main.tscn`（一个挂脚本的根节点），所有界面都用 GDScript 动态构建。

**理由**：
- 手写 `.tscn` 的 `ext_resource uid` / `node_paths` 极易出错，且改一个布局要重写文件；
- 纯代码布局可以用 `_layout()` 统一按 `size` 计算，窗口尺寸变化时自适应；
- 便于在无头模式下实例化界面做冒烟测试（`.tscn` 反而更麻烦）。

**代价**：想用编辑器的可视化布局器就不习惯了。取舍见 `docs/00-设计方案.md` 第 7 节。

## 1. 卡牌坐标不进容器

**决策**：手牌与槽位里的 `CardView` 统一挂在 `_card_layer`（全屏 Control，鼠标透传）下，
由 `_layout_hand()` 手动算坐标，用 Tween 补间。

**理由**：要在"手牌 → 槽位"之间做平滑飞入动画，进容器就得跟容器布局打架；
手动坐标可以精确控制弧线、缩放、层级。

**关键点**：
- `_card_layer.mouse_filter = MOUSE_FILTER_IGNORE`，但子节点 `CardView` 是 `STOP` —— 父节点忽略不影响子节点收事件；
- 飞入时 `view.z_index = 2` 抬到前面，否则卡会滑到别的卡下面；
- 布局变化时先 `_tween_to` 旧的再 kill，避免叠加补间。
