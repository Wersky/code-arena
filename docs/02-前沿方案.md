### 1.2 缺的（金铲铲机制的硬前提）

**现状：14 件道具，13 个不同 family，多数 family 只有 1 件。**

```
训练流   : rlhf / dpo / sft / distill / prompteng   (5 件，但 family 各不相同)
本土系   : kimo / glmio / kweno                      (3 件，family 也各不相同)
推理系   : deepdeek / chatppt                        (2 件)
多模态   : gemigo                                   (1 件)
实时     : grock                                    (1 件)
长文     : mistryl                                  (1 件)
诗性     : sorana                                   (1 件)
```

**结论 1：现在直接上羁绊是空中楼阁。** 羁绊断点要凑到 2/4/6，而"多模态"只有 1 件，
永远触发不了二档。**道具池扩充是金铲铲机制的前置条件，不是配套工程。**

**结论 2：单标签撑不起双轴。** TFT 的羁绊之所以能同时存在"种族流"和"职业流"，
是因为每个单位带**两个标签**（例：暗夜森林 + 刺客）。我们现在的道具只有一个 `family`，
硬加第二轴时必须**新增字段**而不是复用。

**结论 3：AI娘与道具的显示名撞车。** `ai_data.gd` 的 AI娘 `deepdeek/chatppt/kweno/grock`
与 `ai_item_pool.gd` 的道具 `deepdeek/chatppt/kweno/grock` **同 id 同名**。
羁绊面板一旦同屏显示就会歧义（"DeepDeek" 指人还是指道具？）。
需要区分显示名（如道具侧叫「DeepDeek 徽章」），或把道具 id 改成 `item_deepdeek`。

## 2. 核心方案：把金铲铲的"阵容"翻译成提示词的世界

### 2.1 双标签体系（对应 TFT 的种族 + 职业）

**阵营轴 `family`（7 个，粗粒度，是"我这一局是什么流派"）**

| family | 现有道具 | 目标件数 | 定位 |
|---|---|---|---|
| `训练流` | rlhf / dpo / sft / distill / prompteng | 5 | 后训练派，断点 2/4/6 |
| `本土系` | kimo / glmio / kweno | 3 | 中文优化，断点 2/3 |
| `推理系` | deepdeek / chatppt | 2 | 深度思考，断点 2/3 |
| `多模态` | gemigo | 1 | 需扩到 3 |
| `实时` | grock | 1 | 需扩到 3 |
| `长文` | mistryl | 1 | 需扩到 3 |
| `诗性` | sorana | 1 | 需扩到 3 |

> 现状 14 件里 5 件家族各不相同却都属于"训练流"——说明**"训练流"本来就是隐含的第二轴**，
> 只是被塞进了 `family`。这条证据直接支持双标签方案。

**档位轴 `weight`（3 个，正交于阵营，是"这一局走轻装还是重载"）**

| weight | 判定 | 效果方向 |
|---|---|---|
| `轻量` | token 成本 ≤ 1 且无附加约束 | 命令行短、回合多、分数低 |
| `标准` | 中庸 | — |
| `重载` | 多模态 / 联网 / 长文 / 对齐 类 | 单回合分数高，token 预算压力大，命令行长 |

`weight` 直接接到已有的 `token_budget` 与 `token_cost` 字段上，**零新增数据管线**。

### 2.2 羁绊数据模型（新增 `TraitData`）

```gdscript
class_name TraitData extends Resource

@export var id: String = ""              # tr_multimodal
@export var display_name: String = ""    # 多模态共振
@export var axis: String = ""            # "family" | "weight" | "heroine"
@export var match_family: String = ""    # 阵营轴匹配值；"" = 不限
@export var match_weight: String = ""    # 档位轴匹配值；"" = 不限
@export var required_ai: String = ""     # 需要核心 AI娘 id；"" = 不限
@export var breakpoints: PackedInt32Array = PackedInt32Array()  # 断点，如 [2,4,6]
@export var tiers: Array[Dictionary] = [] # 每档：{flat, mult, overrides, note}
```

**这是主人在需求里说的"道具达到什么种类 + 什么 AI 角色触发阵容机制"的直接翻译：**

- `match_family` / `match_weight` → **道具达到什么种类**
- `required_ai` → **什么 AI 角色**
- 两者用 `and` 组合 → **同时满足才触发**

### 2.3 三轴羁绊示例（真实可落地，括号内为现有道具）

**A. 阵营羁绊（纯计数）**

| id | 名称 | 断点 | 档位效果 |
|---|---|---|---|
| `tr_train` | 后训练流水线 | 2 / 4 / 6 | 2：训练法道具 +5 分/件；4：每回合可把一件训练道具的档位**升级**（不消耗回合）；6：升级不占用 token 预算 |
| `tr_cn` | 本土共鸣 | 2 / 3 | 2：中文值 +10；3：命令行 ≥120 字符不再受"冗长"惩罚 |
| `tr_reason` | 推理闭环 | 2 / 3 | 2：--task 居中 +12；3：顺序层倍率下限从 0.50 提到 0.72 |

**B. 档位羁绊（正交轴）**

| id | 名称 | 断点 | 档位效果 |
|---|---|---|---|
| `tr_heavy` | 重载协议 | 2 / 4 | 2：token 预算 +2；4：每回合首个片段免 token 成本 |
| `tr_light` | 轻装上阵 | 2 / 4 | 2：每回合多 1 次重掷；4：重掷不再消耗回合 |

**C. 条件羁绊（阵营 + AI娘，主人要的那种）**

| id | 名称 | 条件 | 效果 |
|---|---|---|---|
| `tr_cn_kweno` | 本土共鸣·中文优化 | 本土系 ≥2 **且** 核心 AI娘 = kweno | 中文片段计分 ×1.15，且 kweno 的"中文流畅"规则不再要求 ≥3 段 |
| `tr_realtime_grock` | 实时情报网 | 实时系 ≥2 **且** 核心 AI娘 = grock | 时效词命中额外 +18；每关可刷新 1 次目标分显示（盲盒加成翻倍） |
| `tr_multimodal_gemigo` | 多模态共振 | 多模态 ≥2 **且** 持有 gemigo | `--knowledge` 片段触发两次计分（注意：这是**触发型**效果，见 §3.3 配平规则） |
| `tr_train_prompteng` | 方法论闭环 | 训练流 ≥3 **且** 持有 prompteng | 规则表每命中一条 `str_`，额外 +2 分（把"结构工整"直接换成钱） |

**AI娘 × 羁绊的交叉是这套系统的心脏**：同一个本土系羁绊，挂 Kweno 是一条路，挂 ChatPPT 是另一条。
这就是"阵容"带来的分支深度——对应 TFT 里"同一羁绊不同单位组合强度不同"。

### 2.4 羁绊在评分引擎里的挂载方式（不破坏既有契约）

**关键约束：`tests/verify_c4.gd` 的四个算例必须仍然逐字等于 1228 / 1045 / 799 / 113。**
办法：**羁绊只在持有道具时生效**——C.4 算例不持有任何道具 → 分数不变 → 回归测试零改动通过。

挂载方式：**新增一层，不新增规则**。现有 `ai_taste.gd` 已有 `scope="item"` 的先例
（`ITEM_MULT_EFFECTS`），照抄这个模式加 `scope="trait"`：

```gdscript
# Scoring.evaluate 的 ctx 新增一个键（字典加键不破坏既有调用方）
# ctx["traits"] = { "tr_train": {tier:2, flat:15, mult:1.0, overrides:{}}, ... }
```

分数公式（在既有公式外层再包一层，形状不变）：

```
final = maxi(0, round((base + flat_generic + flat_trait) × mult_generic × mult_order × mult_trait) + flat_order − 罚分)
```

**规则层倍率钳制 `[0.50, 1.20]` 保持不变**；羁绊倍率单独乘在其后，上限另设（例如 ≤ 1.60），
这样即便羁绊叠满也不会让"顺序"这一核心价值锚点被稀释——顺序层的价值锚点是
**好结构 +32.2% / 乱结构 −14.0%**，这条锚点必须在整个系统里持续可见。

**`overrides` 是规则改写通道**（不是新规则），支持有限几个标志位：

```
order_mult_min      # 抬高顺序层倍率下限（tr_reason 3 档用）
ignore_order_penalty# 顺序层不再扣分，只取消加成（宽容流派）
flat_order_floor    # 顺序层加分的地板值
extra_turn          # 每关 +1 回合
free_reroll         # 重掷不消耗回合
reroll_per_turn     # 每回合可重掷
token_bonus         # token 预算增减
double_knowledge    # --knowledge 计分两次
```

规则引擎在计算顺序层时读 `ctx["traits"]` 里的这些字段。
**这是本方案里最重要的工程决策**：羁绊能力用"改写既有规则"实现，
而不是"再加 40 条规则"。规则表从 39 条膨胀到 80 条会同时拖慢理解、
拖慢验证、拖慢平衡迭代。

### 2.5 AI娘解锁：从"打通第 N 关"改成"达成某个阵容"

现状：AI娘按**章节**解锁（Kweno 通 L3 / ChatPPT 通 L6 / Grock 通 L9）。

前沿改法（TFT 玩法的直译）：**解锁条件绑定到羁绊断点**——
玩家为了解锁 Kweno，必须先在本局里凑出「本土系 ≥2」并且**用本土系道具打过一次带中文的关卡**。

这样两个系统才真正咬合，而不是各玩各的：

- 现在的结构：**关卡进度** → 解锁 AI娘 → AI娘给口味加成。
- 改后：**构筑阵容** → 解锁 AI娘 → AI娘给口味加成 → 口味加成让阵容更强 → 解锁下一位。

关键收益：玩家有了**明确的构筑目标**（TFT 玩家的乐趣核心是"我要凑齐这套"），
而不是"打到 L6 就白送一个 Kweno"。而且这天然制造了"第一局玩推理系、第二局玩本土系"的
重复游玩动机——不同阵容对应不同 AI娘，AI娘口味又和对应羁绊交叉，**阵容选择真正影响玩法**。

实现上几乎零成本：现有 `AiData.locked` / `unlock_hint` 已是字段，
把解锁判定从 `level_index >= N` 换成 `trait_progress(trait_id) >= tier && flag_set(trait_id)`。

### 2.6 「阵容面板」UI（TFT 羁绊面板的翻译）

TFT 的羁绊面板是**这个品类可读性的核心资产**：玩家随时知道"我离下一档差几张"。
我们现在的左竖栏 HUD（LEVEL / TOKEN / COMPUTE / AI）正合适挂载：

```
阵容
训练流    2/4  ▓▓░░   后训练流水线
本土系    1/3  ▓░░░   本土共鸣
推理系    2/3  ▓▓░░   推理闭环
重载      1/2  ▓░░░   重载协议
```

要点：
- 只显示**已激活的轴**和**离下一档最近的那一条**，避免一屏 7 行噪声；
- 下一档的效果**直接写在面板上**（"2：每回合可把一件训练道具的档位升级"），
  这是"玩家为什么买这个道具"的唯一提示来源；
- 激活瞬间：面板该行闪一次 + 一声提示音 + AI娘形象轻微发光。

## 3. 小丑牌侧：种子、大数字、反馈

### 3.1 种子系统升级（现在只有"每关独立种子"）

现状 `run_state.gd`：`run_seed = rng.randi()`，每关 `rng.seed = run_seed + level.id.hash()`。
问题：**单一 RNG 流**。任何一处多抽/少抽一次随机数，后续所有结果全漂移；
`ai_item_pool.roll_rewards` 和 `card_pool.random_cards` 共用同一个 `run.rng`。

**前沿做法（Slay the Spire 每日挑战 / 种子分享通行做法）：**

1. **按用途分流**：每个用途一条独立 RNG 流，种子由主种子派生。
   ```gdscript
   func _stream(purpose: String) -> RandomNumberGenerator:
       var r := RandomNumberGenerator.new()
       r.seed = run_seed ^ ("%s|%d" % [purpose, run_seed]).hash()
       return r
   ```
   用途：`deck` / `reward` / `shop` / `flavor` / `bluff`（Grock 的随机判定）。
   好处：商店多刷一次不会污染牌序；某条支线改动不影响其他支线的复现。

2. **顺序无关选取（哈希选取）**：不要"顺序抽 N 个"，改成
   `pool[hash(purpose + ":" + item_id + ":" + level_id) % pool.size()]`。
   好处：新增一件道具、调整池子顺序，都不会破坏老种子的复现——
   这对**每日挑战的历史榜单**是硬需求。

3. **种子可读可分享**：`PROMPT-2026-10-21` 这种人类可读串 → hash → int。
   UI 上给"复制种子"按钮，输入框支持粘贴别人的种子。

4. **存档带 RNG 状态**：Godot 4 的 `RandomNumberGenerator.state` 是 uint64，存下来即可
   精确续跑（不只是"重开一局"，是"读档接着打，分毫不差"）。

5. **每日挑战**：日期 → 固定种子 + **固定修饰符**（StS 式），
   例如"今日：不可使用重掷" / "今日：token 预算 −2"。修饰符要在**开局前展示**——
   StS 的教训是修饰符不预告会让玩家直接不玩。

### 3.2 大数值：先别上 BigNum，先把死亡墙设计掉

Balatro 的机制死亡点是有名的：**ante 39，目标分超出 double 的 e308 → 变 Infinity → 除法得 NaN →
NaN 永远不等于目标分 → 卡死**。它不是 bug，是"用 float 承载指数增长"的必然结果。

我们这一局如果叠上羁绊倍率 + 触发型效果，分数会比现在（千级）高一到两个数量级。
**必须现在就处理，否则是重写级返工。**

**方案（三条，按工程量排序）：**

| 方案 | 做法 | 成本 | 上限 |
|---|---|---|---|
| **A（推荐）** | 分数全程 `int64`（GDScript 的 `int` 就是 64 位）；**禁止"总分平方/总分相乘"类规则**；显示层做科学计数格式化 | 小 | 9.2e18 |
| B | 自写 `BigNum`（尾数 + 指数） | 中（~120 行 + 全链路改类型） | 无上限 |
| C | 保持 float | 0 | e308，且 NaN 卡死 |

选 A 的理由：GDScript 的 `int` 是 int64，**9.2e18 对本游戏绰绰有余**——
现有目标分 950~3500，即使带上羁绊与触发型效果，整局到 1e12 量级完全够。
真正的风险不是"上限不够"，而是"规则里出现了分数自乘"（`score = score × score`）
或"把分数取对数后再取幂"这类操作——**这些必须从规则设计阶段就禁掉**。

配套两条：
- **显示格式化**：`format_score(v)` —— < 1e6 显示原样；≥ 1e6 走 `1.23e9` 风格；
  再往上加后缀（K/M/B/T/aa/ab…）直到 e 记法。
- **护栏测试**：在测试里断言"所有规则组合下 score 不超过 1e15"，
  以及"分数永远 > 0（除显式罚分外）"。

### 3.3 触发型 vs 加成型：配平规则（前沿数学的直接应用）

Ben Stokman 对 Balatro 的推导：把得分写成
`score = base × Π(加成型效果) × Π(触发型效果)`，固定总效果数时，
得分关于"加成型数量"是**开口向下的二次函数**，在**加成型数量 ≈ 触发型数量**时取最大。
如果两者严重失衡（几乎全是加成型），曲线会退化成"线性堆数值"，构筑就失去了拐点，
玩家只是在比谁堆得多。

**对我们的直接约束**（做道具池时必须遵守）：

- 「加成型」道具：+分、加倍率上限、加回合（`tr_train` 2 档、`tr_reason` 2 档…）
- 「触发型」道具：让某片段重复计分、每满足条件重算一次（`tr_multimodal_gemigo`、`tr_train_prompteng`）
- **每一档的触发型道具数量，应当与同档的加成型道具数量大致相等**（比例 1:1，容差 ±1）。
- 违反时的症状：某个构筑无论怎么选都是最优 → 立刻回到"解开的谜题"状态。

同时，AM–GM 不等式给了一条常被忽略的结论：**给"当前较小的那一侧"加成，收益更大**。
我们的分数是"基础分 × 倍率"，所以"加 20 分"和"加 0.5 倍率"不是等价资源。
→ `AiItemData.power` 这个字段现在是摆设，应该拆成
`chip_power` 与 `mult_power` 两个**独立预算**，平衡时分别记账。
TFT/宝可梦式伤害平衡（Temple of the Roguelike 的二次回归法）也是同一个思路：
不同强度的加成要放在同一把尺子上量。

### 3.4 反馈：把"因果"做成动画（Balatro 最值钱的一条）

Balatro 的核心不是算术，是**结算流水**：每个 Joker 按顺序脉冲触发，
每一跳的贡献被显示出来，running total 逐次跳动。
一个 300ms 的动画，替代了整本说明书——玩家打几手就懂了道具怎么协同。

我们的情况更需要：顺序层有 **39 条规则**，纯数字玩家永远学不会。

**做法：把 `Scoring.evaluate` 的返回值加一个 `breakdown` 有序数组。**

```gdscript
# evaluate 返回值新增一个键（加键不破坏既有调用方与既有测试）
"breakdown": [
  {"src": "base",      "kind": "base",  "flat": 58,  "mult": 1.00, "note": "基础分"},
  {"src": "str_clean", "kind": "rule",  "flat": 15,  "mult": 1.05, "note": "标准序"},
  {"src": "tas_dd_grounded","kind":"taste","flat": 8, "mult": 1.00, "note": "接地思考"},
  {"src": "tr_train",  "kind": "trait", "flat": 15,  "mult": 1.00, "note": "后训练流水线 2档"},
  {"src": "itm_gemigo_knowledge","kind":"item","flat": 0,"mult": 1.08,"note": "多模态素材加成"},
]
```

结算界面按数组顺序逐条播放：每条 120~200ms，
显示「谁贡献了多少 / 当前总分」，命中的规则高亮，倍率条用不同颜色区分加法与乘法。

**收益**：规则系统从"黑箱"变成"可读"；羁绊的价值第一次被玩家看见；
这同时是教学、反馈和"大数字美丽"的表现载体。

### 3.5 音与画（juice 的最小可用集）

- **音高随倍率上升**：结算每命中一条倍率规则，音高上移一档（半音阶），
  玩家能"听出"这次构筑有多猛（Ramone 的 rising pitch 手法）。
- **数字滚动**：总分跳到 1e9 时不要瞬间跳，用滚动 + 轻微过冲。
- **屏幕震动**：只在里程碑（破纪录、激活新羁绊档位）触发，强度随里程碑层级递增。
- **顺序层的因果动画**：命令行里哪一段是 `--role`、哪一段顺序错了，
  在结算时用颜色标出来（绿=位置正确、红=错位、黄=重复 flag）。
  这是"提示词顺序就是一切"这个核心设计**唯一能被玩家看懂的方式**。

## 4. 关卡生成：从手写表到"模板 + 可达性预言机"

### 4.1 现状问题

`level_pool.gd` 手写 10 关。上一轮实测已经暴露过：**"禁打某类卡"式规则会砍掉得分天花板，
逼得目标分下调，曲线出现回退**，玩家看着像 bug。
手写表的根本问题是**难度曲线只能靠人肉感觉对齐**，且改一关要重跑全部。

### 4.2 前沿做法（PCG 的"可解性"方向）

FDG / PCG Workshop 近年的一类工作（Sturgeon-MKIII 的"同时生成关卡与通关演示"、
"Solution Path Heuristics for Predicting Difficulty"）的核心思想是：

> 生成时**同时产出一条可行解**，或至少保证生成后有一个预言机能判断难度。

对我们来说，预言机**已经存在**：`tools/balance_sim.gd` 就是"贪心机器人能不能过"的裁判。

**方案：关卡从"模板 + 修饰符"生成，生成完立刻跑 sim 判定可达性，不可达就重roll。**

```
生成流程
  1. 抽模板（任务类型 + 章节 + 规则骨架）
  2. 抽修饰符（token 预算 / 规则 / 目标分候选）
  3. 跑 balance_sim 判定：该关在 N 个种子下的贪心通过率
  4. 通过率落在 [55%, 92%] → 接受；否则回到 2 换修饰符
  5. 记录该关的统计量（贪心中位数 / 10 分位），用于下一关的目标分推导
```

目标分不再手写，改成 **`目标分 = P10(贪心得分) × 0.7`**，取自同一批种子的实测分布——
这正是本项目 `balance_sim.gd` 已经在用的锚点法，只是把它从"每关手调一次"
升级成"生成时自动定"。

**收益**：
- 关卡数从 10 → 30+ 只是改一个池子；
- 曲线单调递增是**构造保证**的，不是人肉调出来的；
- 每天挑战可以现生成 N 关（同一修饰符池、不同种子）。

### 4.3 蒙特卡洛的三点升级（Phenry Ewing 方法）

现有 `balance_sim.gd` 只有一种"贪心机器人"，所以模拟出来的通过率其实是**上界**。
前沿做法（Phenry Ewing《A Million Little Players》）：

1. **多策略模拟**：至少三种代理——贪心 / 保守（只打高分牌型）/ 随机。
   区间 `[贪心通过率, 随机通过率]` 才是玩家体验的**真实包络**。
   目标：贪心 ≈ 85%，随机 ≈ 25%，说明关卡既可解又有技术空间。
2. **跑量**：当前 120 次。放到 2000~5000 次并输出**置信区间**，
   而不是单点值。关卡生成时用"区间下界"做可达性判定，避免"这次运气好"被误判为可行。
3. **模拟必须包含完整 Run**（现在 `_full_run()` 已经有了 ✅），且要**跨种子**，
   因为羁绊一旦引入，"这局能不能拿到那件道具"就成为一整类新的运气变量。

另外，`TARGET_QUANTILE = 0.10` 这个选择本身是对的（用低分位定目标分，
保证"运气不好也能过"），但要**同时看 P50 和 P90**：
P50 远高于目标分 → 关卡太松；P10 远低于目标分 → 关卡对运气差的人是纯劝退。

## 5. 羁绊引入后的平衡影响清单（必须逐条核对）

| 风险 | 症状 | 对策 |
|---|---|---|
| 规则表膨胀 | 39 → 80 条，玩家学不动，验证变慢 | 羁绊走 `overrides` 通道，不新增规则条目 |
| 数值锚点被稀释 | 顺序层的 +32.2% 优势被羁绊倍率盖过 | 羁绊倍率上限单独设（≤1.60），顺序层锚点单列在 UI |
| 一招流 | 某个羁绊在所有构筑里都最优 | 每档给**不同形状**（改上限 / 改规则 / 改回合），不都是加倍率 |
| 触发型泛滥 | 分数指数爆炸，int64 也扛不住 | §3.3 配平规则 + 禁"分数自乘" |
| 道具池膨胀后失衡 | 32 件里必有几件过强 | 稀有度分层 + `min_chapter` + 商店概率表，`power` 拆双预算 |
| AI娘选择变无意义 | 口味规则被羁绊覆盖 | AI娘口味与羁绊**交叉设计**（`tr_cn_kweno` 这类），确保"人 + 阵容"整体最优 |
| 种子复现被破坏 | 老种子跑出新结果 | RNG 分流 + 哈希选取（§3.1） |
| 回归测试炸 | C.4 算例漂移 | 羁绊默认不生效（无道具时），C.4 天然不变 |

## 7. 明确不做的事（前沿共识）

1. **不让 LLM 参与任何计分路径。** 2026 年的行业现实是 80% 管线 / 15% 受限运行时 / 5% 真运行时；
   延迟、成本、公平性、可复现四重问题在实时 LLM 上无解。
   我们的场景更极端——同一个种子必须给出同一个分数，LLM 天生做不到。
   → 只做风味文本，且离线预生成。
2. **不用自由格式的 LLM 输出做游戏数据。** 数字进 `balance.yaml`、文案进 `strings.json`，
   每条出货数据过一遍 schema 校验。数值永远本地、永远可复算。
3. **不把 float 当分数。** int64 + 显示层格式化。
4. **不手写大数字规则。** 需要触发就加"触发次数"，不写"分数 × 分数"。
5. **不靠"更多规则条目"表达羁绊。** 用 `overrides` 改写既有规则。
6. **不在没做 S1 之前就做 S2。** 道具池不够，羁绊就是空壳。
