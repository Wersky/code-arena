## 1. 开工流程（每次接手必做，5 分钟）

```
① 读 docs/进度交接.md        ← 唯一的项目状态真值：做到哪了、下一步是什么
② 读 docs/踩坑手册.md 最近 10 条  ← 别人踩过的坑，别再踩一遍
③ 跑三条回归（见第 4 节）      ← 确认基线是绿的，再动手
④ 看 docs/进度交接.md §2.3 "账实不符"  ← 这里列的才是真正该干的活
```

**不要凭记忆干活。** 文档和代码不一致时，以代码为准，并顺手把文档改对。

## 2. 分工与认领

### 2.1 认领方式

仓库的 **Issue** 就是任务板。开工前：

1. 看有没有自己名字的 issue；没有就新建一个，标题写清要做什么
2. 在 issue 里留一条 `🔧 开始：<一句话> · <时间>`
3. 干完留 `✅ 完成：<改了什么> · <时间>` 然后关掉

**同一个 issue 不要两个人同时动。** 想接手别人的，先在 issue 里 @ 对方确认。

### 2.2 按文件分工（降低冲突）

| 区域 | 主要归属 | 说明 |
|---|---|---|
| `scripts/core/` `scripts/data/` | 谁改谁负责 | 改动必须同步更新 `docs/04-基础玩法.md` |
| `scripts/ui/` | 谁改谁负责 | 改完必须截图目检 |
| `tools/` 出图脚本 | 谁写谁负责 | 参数约定见第 5 节 |
| `docs/shots/` 卡面 | **一轮只由一个人出** | 出图中途换人会导致角色形象不统一 |
| `docs/进度交接.md` | **每轮收尾都更新** | 冲突最多，改完立刻提交 |

### 2.3 分支策略

**小改动直接提交 `main`。** 大改动（重构、换机制）开分支 `feat/<短名>`，做完 PR。

提交信息格式：

```
<类型>: <一句话>

类型: feat / fix / docs / art / balance / test
例：art: 补完方块 2-10 JQK 的卡面（鲸鱼女仆橙发版）
     fix: 出图脚本拿旧图冒充结果（加新鲜度校验）
```

## 3. 交接纪律（最重要的一条）

**每轮工作结束前，必须把 `docs/进度交接.md` 更新到"下一个人能直接接手"的程度。**

具体要写清：

1. **§2 当前状态**：哪些模块动了、动到什么程度
2. **§2.3 账实不符**：你留下的坑、半成品、还没接进游戏的素材——**这一节最重要**
3. **§3 下一步**：按优先级排，写清楚"从哪个文件、哪一行开始"
4. 如果改了机制，同步更新 `docs/04-基础玩法.md` 和 `踩坑手册.md`

> 判断标准：**一个没参与过这轮工作的人，只看文档能不能直接开工。**
> 不能，就是没交接好。

## 4. 回归基线（改动前后都要绿）

```bash
PROJ="D:/zcode-work/godot/projects/prompt-arena"
GODOT="D:/zcode-work/godot/engine/Godot_v4.7.2-stable_win64_console.exe"

"$GODOT" --headless --path "$PROJ" --script res://tests/smoke_test.gd      # 169 项 0 失败
"$GODOT" --headless --path "$PROJ" --script res://tests/_meme_selftest.gd  # 219 项 0 失败
"$GODOT" --headless --path "$PROJ" --script res://tests/verify_c4.gd       # 不匹配 0/4
```

**假绿判据**（踩坑手册坑 28）：输出的用例数**少于**上面的数字，一律按失败处理，
哪怕打印的是「0 项失败」。多半是没跑 `--import` 导致 class_name 解析失败。

## 5. 出图约定（两人共用一套管线）

```bash
# ① 身份锚：三视图 + 正面细节（16:9、白底）
python pictures/gen.py --name <sheet> --style pixel-art --model gpt-image-2.5-1k --ar 16:9 \
  --ref <角色参考图> --subject "..." \
  --action "three standing views side by side: front, side, back, plus one larger front close-up" \
  --composition "clean sheet on pure white background, no text, no labels, no frame" ...

# ② 点数图：用三视图当 ref 批量出（2~10 / JQK 用手势或抱字母表达点数）
python tools/gen_rank_arts.py --suit <spade|heart|diamond|club> --sheet <sheet.png> \
  --look "<角色描写>" --out <suit> --workers 2

# ③ 合成卡面（白底 + 四角角标 + 圆角透明 + 严格居中）
python tools/compose_card_preview.py --src <角色图> --suit <suit> --rank <n> --pip auto --out <out>
```

**硬规矩：**

- 模型固定 `gpt-image-2.5-1k`（2k 撞 145 秒网关超时）
- 并发最多 2（再多 429）
- 参考图尽量只给一张（两张容易 504）
- **不许改角色设定**：四个花色对应表见 `docs/进度交接.md` §2.2，改之前先问主人

## 6. 常见冲突的处置

| 情况 | 怎么办 |
|---|---|
| 两人同时改了同一文件 | 后提交的人 rebase，保留两边语义改动，**不要整段覆盖** |
| 卡面形象不统一 | 停手，回到三视图重新对齐身份锚，别在半途换参考图 |
| 数值争议 | 不听直觉，跑 `balance_sim2.gd` + 多批种子，看数 |
| 文档与代码不一致 | 以代码为准，改文档；若代码本身可疑，记进 `账实不符` 一节 |
| 主人给的指令和文档冲突 | **以主人当次指令为准**，改完把文档同步 |
