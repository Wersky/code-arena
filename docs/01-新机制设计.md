## 0. 阅读指南与术语

| 术语 | 含义 |
|---|---|
| **AI 娘** | 本局选定的核心模型人格，4 选 1。有虚构显示名与独立"口味"。 |
| **命令行** | 本局最终提交给模型的那一段文本，形如 `deepdeek --role "资深工程师" --task "写个函数"`。 |
| **片段（segment）** | 命令行的一段，由一张卡合成，格式固定为 `--<flag> "<value>"`。 |
| **参数名（flag）** | `--role` / `--task` / `--knowledge` / `--format` / `--example` / `--constraint`，由卡类型唯一决定。 |
| **顺序层** | 新增的评分层，负责"顺序与结构"；旧"牌型层"改称**通用层**，负责"选了什么"。 |
| **逆序数 inv** | 片段序列中所有"前段类型序号 > 后段类型序号"的配对个数。inv=0 即标准序。 |
| **规范序** | 角色 → 任务 → 素材 → 格式 → 范例 → 约束（沿用 `CardData.KIND_ORDER`，本表为唯一真值）。 |

| 参数名 | `--role` | `--task` | `--knowledge` | `--format` | `--example` | `--constraint` |

## A. 机制总述与一局流程时序

### A.1 一句话

**把"打牌型"改成"敲命令行"：你选的每一张卡都是一条命令行参数，你的选择顺序就是参数顺序，你敲下去的顺序就是提示词的样子；核心 AI 娘按自己的口味给这条命令行打分。**

### A.2 三大支柱

| 支柱 | 旧机制 | 新机制 |
|---|---|---|
| 提示词长什么样 | 自然语言句子堆叠（`card.body` 拼接） | 一条命令行，参数化、可读、可执行 |
| 顺序有没有意义 | 无（预览面板按 `KIND_ORDER` 自动重排） | **有，且是核心**（规范序加分、乱序扣分） |
| 谁在评分 | 无角色，规则一套 | **核心 AI 娘**按自己的口味挑规则、加权、给台词 |

### A.3 一局流程时序

```
主菜单
  ↓ 「开始新一局」
run.reset_run()                       # ai 置空，command_parts 清空
  ↓
[AI 选择界面 ai_select.gd]  ← 本次改动的入口
  4 个竖排方框：DeepDeek / Kweno / ChatPPT / Grock
  已解锁的可点，未解锁的画成纯黑剪影 + 轮廓 + 锁 + 解锁提示
  玩家点击 → signal ai_chosen(ai)
  ↓ run.set_ai(ai)
[战斗界面 arena.gd + console.gd]
  每回合：
    ├─ 抽 8 张手牌（圆弧扇形）
    ├─ 玩家点击手牌卡
    │    → 该卡片段 "--<flag> \"<value>\"" 被"敲"进控制台命令行
    │    → 打字机效果（见 F.4）：未打完时再点下一张，立刻补全当前片段再打下一段
    │    → 该卡离开手牌，片段进入 run.command_parts（顺序 = 点击顺序）
    ├─ 点击命令行里的某片段 → 该片段移除，卡退回手牌，其后片段自动前移
    ├─ 点击 ⌫ → 移除最后一段（退回手牌）
    ├─ 命令行最多 6 段（对应 6 种 flag），超出则拒绝并提示
    └─ 点「运行」
         → console.finish_all()（把没打完的字立刻补完）
         → Scoring.evaluate(cards, ctx) = 通用层 + 顺序层
         → 控制台下方追加 AI 娘的回应（ResponseGen）+ 分数明细
         → 回合 +1，本回合手牌全部作废重抽
  回合用尽 → 累计分 ≥ 目标分？
    是 → 过关 → 三选一奖励 → （每 3 关）商店 → 下一关（AI 娘不换）
    否 → 失败 → 可重打本关
L10 通关 → 整局结算 → 主菜单
```

### A.4 关键设计约定（跨任务必须一致）

| 编号 | 约定 | 原因 |
|---|---|---|
| A-1 | **命令行顺序 = 玩家点击卡牌的顺序**，不做自动重排。 | 顺序是玩法核心，必须由玩家掌控。 |
| A-2 | **命令行片段上限 = 6**（= 6 种 flag 各一段）。6 段可覆盖规范序全部位置。 | 与 6 种卡类型一一对应，超出无意义。 |
| A-3 | 命令行**允许同种 flag 出现多次**（例如两条 `--format`），但会被规则惩罚。 | 允许犯错，且让"结构"有正反两面。 |
| A-4 | 每回合开始时命令行清空（`run.command_parts.clear()`），本回合打出的卡全部弃牌。 | 与旧机制"整手牌作废重抽"一致。 |
| A-5 | **AI 娘在整局内不更换**（`run.ai` 在 `reset_run()` 时置空，之后只写一次）。 | 口味是整局的构筑承诺，不是每关的临时增益。 |
| A-6 | 换 AI 娘**不影响**牌库、道具、算力、关卡进度（详见 H.3）。 | 避免"换人刷分"。 |

## B. 命令行语法规范

### B.1 语法定义

```
<command> ::= <prefix> WS (<segment> WS)* <segment>
<segment> ::= <flag> WS '"' <value> '"'
<flag>    ::= "--role" | "--task" | "--knowledge" | "--format" | "--example" | "--constraint"
<value>   ::= 卡牌的 cli_token 字段内容，内部若含双引号须转义为 \"
<prefix>  ::= AI 娘的 id（小写），如 deepdeek
```

- **分隔符**：片段之间恰好 **1 个半角空格**；片段内部 `--flag` 与 `"value"` 之间恰好 **1 个半角空格**。
- **引号**：值**始终**用一对 ASCII 双引号包裹（中文值也加），保证解析无歧义。
- **显示形态**（控制台第一行）：

```
C:\PROMPT_ARENA> deepdeek --role "资深工程师" --task "写个函数" --format "输出一段 JSON"
```

### B.3 顺序的语义（明确回答"角色是否必须最前、约束是否必须最后"）

| 位置要求 | 规则 | 强制程度 | 未满足的后果 |
|---|---|---|---|
| `--role` 必须最前 | `str_role_head` / `str_no_role_head` | **硬性**（有角色时） | 命中 `str_no_role_head`：×0.93、−16 分 |
| `--constraint` 必须最后 | `str_constraint_tail` / `str_constraint_broken` | **硬性**（有约束时） | 命中 `str_constraint_broken`：×0.95、−12 分 |
| `--task` 在 `--role` 之后 | `str_task_anchor` / `str_task_misplaced` | 软性（有任务时） | 命中 `str_task_misplaced`：−10 分 |
| `--format` 在 `--example` 之前 | `str_format_before_example` | 软性（两者都有时） | 不满足：0 分（不扣，只是拿不到 +6） |
| `--knowledge` 紧邻 `--task` | `str_adjacent_task_knowledge` | 软性 | 不满足：0 分（不扣） |

> 即：**角色在前、约束收尾是硬性顺序要求；其余只给正向奖励。** 这两条是"命令行思维"的最小闭环——先定义"你是谁"，最后声明"边界在哪"。

### B.4 规范序与逆序数

- **规范序** = 片段类型序号严格递增（可缺项）。例：`--role --task --knowledge --format --example --constraint`（6 段）为规范序；`--role --task --format --example`（缺素材）也是规范序。
- **逆序数 inv** = 所有满足 `i < j 且 seq[i] > seq[j]` 的配对个数。同类型（序号相等）不算逆序。
  - 例 A：`role task knowledge format example constraint` → inv = 0。
  - 例 B：`task role knowledge format example constraint` → inv = 1（只有 task/role 这一对）。
  - 例 C：`task knowledge role format example constraint` → inv = 2（task>role、knowledge>role）。
- inv 直接映射到 4 条分层规则：`str_clean`(0) / `str_one_swap`(1) / `str_messy`(2) / `str_scramble`(≥3)。

### B.5 参数值长度规则

| 项 | 限制 | 违规处理 |
|---|---|---|
| 单个 `cli_token` 长度 | **≤ 20 个字符**（含中文按 1 字计） | 数据层拒绝入库（`CardPool` 不写超长值）；`CardData` 提供 `is_cli_token_valid()` 校验 |

## C. 有序结构评分模型（顺序层规则表）

### C.1 总公式

顺序层与通用层是**两层独立相加再相乘**的关系。完整结算公式（`Scoring.evaluate` 内必须严格按此顺序）：

```
base        = Σ 卡基础分（含关卡规则修正、道具修正、约束卡 ×2）
flat_generic= Σ 通用层（牌型）加分 + Σ 道具加分
mult_generic= Π 通用层（牌型）倍率 × Π 道具倍率

flat_order  = Σ 命中的通用顺序规则 flat + Σ 命中的口味规则 flat
mult_order  = (Π 命中的通用顺序规则倍率) × (Π 命中的口味规则倍率)
              上限 1.20，下限 0.50

最终分 = maxi(0,
        round((base + flat_generic) × mult_generic × mult_order)
        + flat_order
        − 超预算罚 − 幻觉罚)
```

**为什么 `flat_order` 放在乘法之外**：`flat_order` 是"结构对了就多给分"的**奖金**，不参与倍率放大；
否则规则表会被高倍率牌型（如完美配方 ×1.50）二次放大，分数失控。
这一条是硬约定，实现时不得写成 `round((base + flat_generic + flat_order) × ...)`。

### C.2 通用顺序规则表（`str_` 前缀，4 位 AI 娘**全部**共享，永远参与判定）

| 规则 id | 名称 | 条件 | 倍率 | 加分 | 触发次数 |
|---|---|---|---|---|---|
| `str_empty` | 空命令行 | 片段数 = 0 | ×1.00 | 0 | 至多 1 次 |
| `str_len_2` | 双要素 | 片段数 = 2 | ×1.00 | +10 | 至多 1 次 |
| `str_len_3` | 三要素 | 片段数 = 3 | ×1.00 | +14 | 至多 1 次 |
| `str_len_4` | 四要素 | 片段数 = 4 | ×1.00 | +18 | 至多 1 次 |

### C.3.1 道具顺序层效果（scope = `item`，**不属于 39 条规则表**）

> **背景**：道具 `Gemigo`（多模态）原效果是"每回合可额外挂 1 张 素材 卡（不占 5 个槽位）"，
> 而新机制把命令行上限定成 **6 段**、第 7 段必拒 → 该效果**实现不出来，道具等于白给**。
> 现改为**在 6 段上限下能成立**的效果：**多模态 = 素材越多越强**。

| 规则 id | 名称 | scope | 条件 | 倍率 | 加分 | 归属 |
|---|---|---|---|---|---|---|
| `itm_gemigo_knowledge` | 多模态素材加成 | `item` | 命令行含 `--knowledge` 片段 | **×1.08** | 0 | 道具 `Gemigo`（`AiItemPool`，effect_id = `knowledge_mult`） |

**层级与钳制（实现必须一致）**

| 项 | 规则 |
|---|---|
| 规则层（23 条 `str_` + 16 条 `tas_`） | 倍率乘积**仍钳制在 `[0.50, 1.20]`**（`AiTaste.evaluate` 内部不变） |

### C.5 顺序层在总分里的实际权重（算例，供 G 章节引用）

**方法签名（逐字）**

```gdscript
## 主入口：对一条命令行评分。
## parts      = 参数片段数组，每项形如 `--role "资深工程师"`（含引号）

## 返回 [{arg:String, value:String, kind_index:int, pos:int}, ...]
```

**返回值字典的键与类型（严格）**

| 键 | 类型 | 含义 |
|---|---|---|
| `score` | `int` | 顺序层总加分 = 通用顺序规则 flat 合计 + 口味规则 flat 合计（**可负**） |
| `mult` | `float` | 顺序层**规则层**倍率 = Π 通用顺序规则倍率 × Π 口味规则倍率（钳制在 `[0.50, 1.20]`）。**不含道具层**（道具层见 `item_order_mult` / C.3.1） |
| `combos` | `Array[String]` | 命中的规则 id 列表，按 `rule_table()` 的顺序排列 |
| `notes` | `Array[String]` | 每条命中规则的中文评语，格式见 D.3 |

**`evaluate` 的执行顺序（实现必须一致）**

1. `if parts.is_empty()` → 返回 `{"score":0, "mult":1.0, "combos":["str_empty"], "notes":["命令行是空的——我什么都没收到。"]}`。
2. `var parsed := parse(parts)`；`var inv := inversions(parsed)`。
3. 按 C.2 逐条判定通用顺序规则 → 收集 `universal_hits`。
4. 若 `ai != null`，取 `ai.taste_rules`，按 C.3 逐条判定口味规则 → 收集 `taste_hits`。
5. `score = Σ(hit.flat)`；`mult = Π(hit.mult)`，再 `clampf(mult, ORDER_MULT_MIN, TASTE_MULT_MAX)`。
6. `combos = 所有命中规则的 id`（通用在前，口味在后，各按规则表顺序）。
7. `notes = 每条命中规则一句中文评语`。

**`parse` 的解析规则（逐字）**

- 用正则 `^(--[a-z]+)\s+"((?:[^"\\]|\\.)*)"$` 匹配每段；匹配失败的片段按 `arg = ""`、`value = 片段原文`、`kind_index = -1` 处理，**不计入逆序**，也不触发任何基于位置的规则。
- `value` 中的 `\"` 还原为 `"`。
- `kind_index = KIND_INDEX.get(arg, -1)`。

**道具层（2.6）：Gemigo 多模态**

```gdscript
# ── 2.6 道具层（顺序层倍率）──────────────────────────
```

**最终公式（原 `var score := int(round((base + flat) * mult))` 必须替换为）**

```gdscript
var score := int(round((base + flat) * mult * order_mult)) + order_flat
score = maxi(0, score - overflow_penalty - hallucination_penalty)
```

## G. 平衡锚点

### G.1 现状基线（改造前实测值）

| 关卡 | 贪心均分（实测） | 当前目标分 | 目标分 / 贪心均分 |
|---|---|---|---|
| L1 | ≈ 1500 | 950 | 0.633 |
| L6 | ≈ 3500 | 2450 | 0.700 |
| L10 | ≈ 5700 | 3900 | 0.684 |
| 整局通关率 | — | — | **41%** |

> 注：任务卡里写的目标分「950 / 2350 / 3700」与 `scripts/data/level_pool.gd` 的实际值 `950 / 2450 / 3900` 不一致，**以代码为准**（本文档按 950 / 2450 / 3900 计算）。
> 其余 7 关的贪心均分未在任务卡中给出，改造后必须**重跑 `tools/balance_sim.gd` 补齐**。

### G.2 新加成层让分数上浮多少（三个来源分解）

| 来源 | 影响量 | 说明 |
|---|---|---|
| ① 顺序层（结构正确、规范序） | **+32.2%** | 见 C.5 例 1：929 → 1228 |
| ② 顺序层（结构糟糕、乱序） | **−14.0%** | 见 C.5 例 3：929 → 799 |
| ③ 片段上限 5 → 6 | **+4% ~ +8%** | 单回合多一张卡，base 多 10~18 分、通用 flat 多 0~100 分；但 Token 也多 1~2，L1/L2 会更紧 |
| ④ 完美配方条件放宽 `size >= 5 and distinct >= 5` | **0% ~ +12%** | 6 段全异类型时该 jackpot 仍触发，5 段时照旧 |

**综合估算**：熟练玩家（会排顺序、会凑 6 段）的单回合/单关得分上浮 **+38% ~ +42%**；
只会按类型堆牌、不管顺序的玩家得分 **−10% ~ 0%**（顺序层吃掉的分数抵消了片段上限的收益）。

> **2026-10-21 复核**：①② 两项是用修正后的 C.5 算例重算的（原文档误写成 +31.8% / −24.7%，源头是我把例 1 的通用顺序层 flat 少加了 8、又漏乘了 `str_no_role_head` 的 ×0.93）。
> ① 从 +31.8% 修正为 **+32.2%**（几乎不变）；② 从 −24.7% 修正为 **−14.0%**（乱序惩罚比原先估计的**温和**）。
> 因为 ① 基本没动，**G.4 的十关目标分不需要改**；只有"乱序玩家"的体感惩罚变小了，见 G.3 的回调规则。

### G.3 目标分建议公式

```
新目标分 = round(旧目标分 × 1.27)
```

**为什么是 1.27**：①（顺序层，规范序）+32.2%，③（片段上限 5→6）+4~8%，合计约 **+38%**；
但目标分不能跟满到 +38%，否则**通关率会从 41% 直接冲到 75% 以上**，难度塌方。
×1.27 的效果是：**贪心均分涨约 38%、目标分只涨 27%**，
于是「目标分 / 贪心均分」从 0.633 降到约 **0.579**（约 −8%）——
刻意让**最优解的过关难度略降**，把每关贪心通过率推到 85% 以上（见 G.5 验收标准），
同时**乱打牌的玩家分数不涨反跌**（−14.0%），两头的差距被拉大。

**交叉校验公式（必须与上式结果接近，偏差 >10% 以重测为准）**

```
新目标分 ≈ round(新贪心均分 × 0.58)
新贪心均分 ≈ 旧贪心均分 × 1.38
```

| 关卡 | 旧贪心均分 | 推算新贪心均分 | 公式线新目标分 | ×1.27 线新目标分 | 取值 |
|---|---|---|---|---|---|
| L1 | 1500 | 2070 | 2070 × 0.58 = 1201 | 950 × 1.27 = 1207 | **1210** |
| L6 | 3500 | 4830 | 4830 × 0.58 = 2801 | 2450 × 1.27 = 3112 | **3110** |
| L10 | 5700 | 7866 | 7866 × 0.58 = 4562 | 3900 × 1.27 = 4953 | **4950** |

> L6 / L10 的两条线偏差在 10%~11%，说明这两关旧目标分本来就比"贪心均分 × 0.58"宽松。
> **以 ×1.27 线为准**（保难度比），并要求实现后重跑模拟复核。
>
> **2026-10-21 复核结论**：C.4/C.5 修正后，① 只从 +31.8% 变到 +32.2%（+0.4 个百分点），

> 按 G.5 的回调规则把目标分整体上调 ×1.12 即可。

## H. 边界情况

### H.1 参数片段过长怎么办 / Token 预算怎么算

**定案（实现必须照抄）**

| 项 | 规则 | 理由 |
|---|---|---|
| Token 花费口径 | **命令行 Token = Σ 卡.token_cost**，**不加任何语法开销** | 旧版每张卡携带一句长 `body`（自然语言），新版换成短的 `cli_token`，命令行本身就是提示词，天然更省 token。不再叠加语法开销，避免 6 段玩法在 L1/L2 必然超预算 |
| 例（6 段标准序） | 资深工程师(1) + 写个函数(2) + 附上报错堆栈(2) + 输出一段 JSON(1) + 给一个正例(1) + 不得编造事实(1) = **8 token** | L1 预算 9 → 不超；L2 预算 11 → 宽松 |
| 超预算罚 | 不变：`overflow × 15`（`OVERFLOW_COST`），L7 `DOUBLE_OVERFLOW` 规则下 ×2 | 保持旧平衡锚点 |
| 单片段长度 | `cli_token` **≤ 20 字符**，`CardData.is_cli_token_valid()` 校验；数据层不入库超长值 | 防止命令行被一个超长值撑爆控制台 |
| 命令行总长 | ≤ 80 → `str_compact` (+8)；> 120 → `str_verbose` (−10)；80~120 之间无奖惩 | 用**结构分**而不是**token 罚**来管长度，避免破坏 token 预算的语义 |
| 控制台显示 | 超过控制台宽度 → 横向滚动，**不截断、不换行改写** | 截断会让玩家看不懂自己敲了什么 |
| 片段数上限 | 6；第 7 段被拒绝（提示「命令行过长（最多 6 段）」），卡留在手牌 | 对应 6 种 flag |

### H.2 锁定的 AI 娘在数据层如何表示

| 层 | 表示方式 |
|---|---|
| `AiData.locked` | `bool`，初始 `false`（DeepDeek）/ `true`（其余 3 位） |
| `AiData.unlock_hint` | `String`，如 `通过 L3 后加入`，显示在锁定方框下方 |
| 解锁判定 | **不在 `AiData` 里**，而在 `AiPool`：`UNLOCK_AT = {"deepdeek":0, "kweno":3, "chatppt":6, "grock":9}`，键 = 已过关关数 |
| 状态刷新 | `AiPool.ai_list_for_select(levels_cleared)` 返回 4 位 AI 娘副本，并按 `levels_cleared >= UNLOCK_AT[id]` 设置 `locked` 与 `unlock_hint` |
| 数据层不缓存解锁状态 | `AiData` 是**静态人格数据**；"锁不锁"是**运行时状态**，由 `ai_list_for_select` 计算后写入副本。禁止把解锁状态硬编码进 `all_ais()` |
| 美术 | 锁定态**不换资源**，由 UI 把形象遮成纯黑剪影 + 轮廓（见 F.3） |

### H.3 换 AI 娘是否影响已有牌组

**定案：整局内 AI 娘不换**（见 A-5）。若将来开放"关卡之间换人"，规则如下：

| 项 | 是否受影响 |
|---|---|
| 牌库 `deck` / 抽牌堆 / 弃牌堆 / 手牌 | **不受影响**，原样保留 |
| AI 道具 `items` / 算力 `compute` / 关卡进度 `level_index` / `chapter` | **不受影响** |
| 本关已敲进命令行的片段 `command_parts` | **会被清空**（`set_ai()` 内 `command_parts.clear()`）——命令行前缀变了，旧片段必须作废 |
| 本关已经结算过的分数 | **不受影响**，已入账的分不回收 |
| 本关剩余回合 | **不受影响**，回合数照旧 |

**为什么不允许局内换**：命令行前缀一变，玩家已经写好的整条命令就换了语义，
会让"AI 娘口味"从构筑承诺退化成每回合的临时增益，破坏整局的规划感。

### H.4 其它边界情况（逐条定案）

| 编号 | 情形 | 处理 |
|---|---|---|
| H-1 | 玩家一张卡都不敲就点「运行」 | 拒绝运行，状态栏提示「命令行不能为空」。`AiTaste.evaluate` 对空数组返回 `str_empty`，得分 0 |
| H-2 | 同一张 flag 出现多次 | 允许（规则表有 `str_dup_flag` 惩罚）；不禁止 |
| H-3 | 撤回某片段时**正在打字** | 先 `console.finish_all()` 把当前片段补全，再 `set_command()` 重排。**任何时候命令行里都不允许出现半截片段** |
| H-4 | 撤回中间某片段 | 其后片段自动前移；对应的卡退回手牌（顺序回到手牌末尾） |
| H-5 | 回合结束时命令行还有内容 | `run.command_parts.clear()` + `console.set_command(ai.id, [])`；本回合用过的卡全部进弃牌堆，手牌补满 8 张 |
| H-6 | 关卡特殊规则（`NEED_FORMAT` / `NEED_KNOWLEDGE` / `HALF_PERSONA` 等） | **完全按类型判定，与顺序无关**，逻辑一字不改 |
| H-7 | 关卡规则 `BOSS`（每回合至少 2 张卡） | 改为"命令行至少 2 段"，逻辑一字不改 |
| H-8 | `ResponseGen` 生成回应 | **不需要改 API**。前提：`arena` 传给 `ResponseGen.compose(cards, score, combos)` 的 `cards` 数组**必须按命令行顺序**（而不是手牌抽取顺序）排列 |
| H-9 | 同一关重打 | `start_level()` 清空 `command_parts`；AI 娘不变；牌库按 `run_seed + level.id.hash()` 重洗，**每关牌序都不同**（既有行为不变） |
| H-10 | `run.ai` 为 null（未选 AI 娘就进战斗） | `AiTaste.evaluate` 只跑通用顺序规则（无口味规则）；`main.gd` 必须保证流程上不会出现这种情况 |
| H-11 | `command_parts` 与 `cards` 数组长度不一致（异常态） | `AiTaste.evaluate` 只吃 `command_parts`；`Scoring` 的通用层只吃 `cards`。两者独立，不会崩。arena 必须保证两者同步（这是 arena 的责任） |
| H-12 | 玩家在 AI 娘选择界面点已锁定的方框 | 无信号，只给一行提示文字（`unlock_hint`） |
| H-13 | 存档 / 读档 | 本作**没有存档系统**，无需处理。`RunState.reset_run()` 会把 `ai` 置空，读档后需重新选 AI 娘 |
